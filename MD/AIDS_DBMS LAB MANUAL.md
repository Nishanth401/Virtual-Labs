Design of ER Diagram and Relational Schema for an E-Commerce System
Date:
Aim:
To design a complete Entity-Relationship (ER) diagram for an E-Commerce System
involving Customers, Products, Orders, Payments, and Suppliers, and to systematically convert the
ER model into a normalized relational schema with appropriate primary keys, foreign keys, and
constraints implemented in MySQL.
Procedure:
The following steps are executed in sequence:
1. Identify all entities in the E-Commerce domain: Customer, Product, Order, Payment, and
Supplier.
2. Identify attributes for each entity and mark primary keys (underlined).
3. Identify relationships between entities and specify cardinalities (1:1, 1:N, M:N).
4. Draw the ER Diagram showing entities, attributes, relationships, and cardinalities.
5. Convert each entity to a relational table (relation) with appropriate column data types.
6. Convert M:N relationships into associative (bridge) tables with composite or surrogate keys.
7. Define all PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, and CHECK
constraints in SQL.
8. Create the database and tables in MySQL using CREATE TABLE statements.
9. Insert sample data (seed data) using INSERT INTO statements.
10. Execute SELECT queries to verify the structure and data.
11. Execute JOIN queries to demonstrate inter-table relationships.
Entities, Attributes, and Keys:
Each entity, its attributes, and its primary key are listed below:
Entity 1 — CUSTOMER
• Primary Key: customer_id (INT, AUTO_INCREMENT)
• Attributes: full_name (VARCHAR), email (VARCHAR, UNIQUE), phone (VARCHAR),
city (VARCHAR), wallet_balance (DECIMAL)
Entity 2 — SUPPLIER
• Primary Key: supplier_id (INT, AUTO_INCREMENT)
• Attributes: supplier_name (VARCHAR), contact_email (VARCHAR), city (VARCHAR),
rating (DECIMAL)
Entity 3 — PRODUCT
• Primary Key: product_id (INT, AUTO_INCREMENT)
• Foreign Key: supplier_id → SUPPLIER(supplier_id)
• Attributes: product_name (VARCHAR), category (VARCHAR), price (DECIMAL),
stock_qty (INT)
Entity 4 — ORDER
• Primary Key: order_id (INT, AUTO_INCREMENT)
• Foreign Key: customer_id → CUSTOMER(customer_id)
• Attributes: order_date (DATETIME), total_amount (DECIMAL), order_status (ENUM)

Entity 5 — ORDER_ITEM (Bridge: ORDER ↔ PRODUCT)
•  Primary Key: item_id (INT, AUTO_INCREMENT)
•  Foreign Keys: order_id → ORDER, product_id → PRODUCT
•  Attributes: quantity (INT), unit_price (DECIMAL)

Entity 6 — PAYMENT
•  Primary Key: payment_id (INT, AUTO_INCREMENT)
•  Foreign Key: order_id → ORDER(order_id)
•  Attributes:  payment_mode  (VARCHAR),  payment_status  (ENUM),  paid_amount
(DECIMAL), paid_at (DATETIME)

SQL Syntax Reference:
The following SQL commands are used in this experiment:
1. CREATE DATABASE
Creates a new database (schema). Must be executed before creating any tables.
CREATE DATABASE database_name;
USE database_name;
2. CREATE TABLE
Creates a table with column definitions, data types, and constraints.
CREATE TABLE table_name (
column_name DATA_TYPE [constraints],
...
CONSTRAINT pk_name PRIMARY KEY (col),
CONSTRAINT fk_name FOREIGN KEY (col) REFERENCES other_table(col)
);
3. INSERT INTO
Inserts one or more rows into a table.
INSERT INTO table_name (col1, col2, ...)
VALUES (val1, val2, ...), (val1, val2, ...);
4. SELECT
Retrieves data from one or more tables; supports filtering, sorting, and joining.
SELECT col1, col2 FROM table_name
WHERE condition
ORDER BY col ASC|DESC;
5. JOIN (INNER / LEFT)
Combines rows from two or more tables based on a related column.
SELECT t1.col, t2.col
FROM table1 t1
INNER JOIN table2 t2 ON t1.id = t2.id;
-- LEFT JOIN: keeps all rows from left table
LEFT JOIN table2 t2 ON t1.id = t2.id;

6. AGGREGATE FUNCTIONS
Perform calculations across multiple rows: COUNT(), SUM(), AVG(), MAX(), MIN().
SELECT customer_id, COUNT(*) AS total_orders,
SUM(total_amount) AS total_spent
FROM Orders
GROUP BY customer_id;

Ex. No: 2
Database Normalization from UNF to BCNF for a University Management System
Date:
Aim:
To identify entities, attributes, relationships, and keys for a University Management System
and to systematically normalize the relational schema through First Normal Form (1NF), Second
Normal Form (2NF), Third Normal Form (3NF), and Boyce-Codd Normal Form (BCNF) to eliminate
all data redundancy, partial dependencies, transitive dependencies, and anomalies.
Procedure:
1. Gather requirements for the University Management System: Students, Courses, Instructors,
Departments, and Enrollments.
2. Start with an Unnormalized Form (UNF) table containing all raw data including repeating
groups.
3. Apply 1NF: Ensure atomic values, remove repeating groups, define a primary key.
4. Apply 2NF: Remove all partial dependencies (non-key attributes depending on part of a
composite key).
5. Apply 3NF: Remove transitive dependencies (non-key attributes depending on other non-key
attributes).
6. Apply BCNF: Verify that for every functional dependency X → Y, X is a superkey
(candidate key).
7. Create the final normalized tables in MySQL with appropriate constraints.
8. Insert seed data and execute queries to verify correctness.
Entities, Attributes, and Keys:
Entity 1 — DEPARTMENT
• Primary Key: dept_id (INT, AUTO_INCREMENT)
• Attributes: dept_name (VARCHAR, UNIQUE), hod_name (VARCHAR), established_year
(YEAR)
Entity 2 — INSTRUCTOR
• Primary Key: instructor_id (INT, AUTO_INCREMENT)
• Foreign Key: dept_id → DEPARTMENT(dept_id)
• Attributes: instructor_name (VARCHAR), email (VARCHAR, UNIQUE), specialization
(VARCHAR)
Entity 3 — STUDENT
• Primary Key: student_id (INT, AUTO_INCREMENT)
• Foreign Key: dept_id → DEPARTMENT(dept_id)
• Attributes: student_name (VARCHAR), email (VARCHAR, UNIQUE), dob (DATE),
admission_year (YEAR)
Entity 4 — COURSE
• Primary Key: course_id (INT, AUTO_INCREMENT)

Normalization Process:
We start with an unnormalized flat table that stores everything about a student, their courses,
and instructor in a single row. We normalize step by step.

Unnormalized Form (UNF) — Raw Data
The following single-table captures all attributes in a flat, denormalized structure:
-- UNF Table (DO NOT CREATE THIS — shown for reference only)
-- StudentID | StudentName | Email | DOB | DeptName | HOD |
-- CourseID  | CourseName  | Credits | Semester | InstructorID |
-- InstructorName | InstructorEmail | Specialization | Grade | AttendancePct
-- PROBLEMS:
--   Repeating groups (a student appears once per course enrolled)
--   No atomic values guaranteed
--   Massive data redundancy

Step 1 — First Normal Form (1NF)
Rule: All column values must be atomic (indivisible). No repeating groups. A primary key must be
defined.
Action: Define composite primary key (StudentID, CourseID). Ensure all cells hold single values.
-- After 1NF the table has ONE row per (Student, Course) pair.
-- Primary Key: (student_id, course_id)
-- Table: StudentCourse_1NF
-- student_id | student_name | email | dob | dept_name | hod_name |
-- course_id  | course_name  | credits | semester |
-- instructor_id | instructor_name | specialization | grade | attendance_pct
-- STATUS: 1NF achieved — atomic values, no repeating groups, PK defined.
-- REMAINING ISSUES: Partial dependencies exist (student_name depends only on
--   student_id, not on the full composite key).

Step 2 — Second Normal Form (2NF)
Rule: Must be in 1NF AND every non-key attribute must be fully functionally dependent on the
entire primary key. No partial dependencies.
Action: Decompose the 1NF table. Attributes depending only on student_id go to a Student table.
Attributes depending only on course_id go to a Course table. Only Grade and AttendancePct depend
on (student_id, course_id) — they stay in the Enrollment bridge table.
-- After 2NF decomposition:
-- Student(student_id PK, student_name, email, dob, dept_name, hod_name)
-- Course(course_id PK, course_name, credits, semester, instructor_id,
-- instructor_name, specialization)
-- Enrollment(student_id FK, course_id FK, grade, attendance_pct)
-- STATUS: 2NF achieved — no partial dependencies.
-- REMAINING ISSUES: dept_name → hod_name (transitive dependency in Student).
-- instructor_name → specialization (transitive dependency in Course).
Step 3 — Third Normal Form (3NF)
Rule: Must be in 2NF AND no non-key attribute may transitively depend on the primary key (i.e., no
non-key attribute depends on another non-key attribute).
Action: Remove transitive dependencies. dept_name and hod_name move to a Department table.
instructor_name and specialization move to an Instructor table.
-- After 3NF decomposition:
-- Department(dept_id PK, dept_name UNIQUE, hod_name, established_year)
-- Student(student_id PK, student_name, email, dob, dept_id FK)
-- Instructor(instructor_id PK, instructor_name, email, specialization, dept_id FK)
-- Course(course_id PK, course_name, credits, semester,
-- dept_id FK, instructor_id FK)
-- Enrollment(enrollment_id PK, student_id FK, course_id FK,
-- grade, attendance_pct, enrollment_date)
-- STATUS: 3NF achieved — no transitive dependencies.
-- CHECK FOR BCNF: Every determinant must be a candidate key.
Step 4 — Boyce-Codd Normal Form (BCNF)
Rule: Must be in 3NF AND for every functional dependency X → Y, X must be a superkey
(candidate key). BCNF is stricter than 3NF — it eliminates anomalies that 3NF sometimes misses.

SQL Syntax Reference:
1. START TRANSACTION / COMMIT / ROLLBACK
A transaction is a logical unit of work that groups one or more SQL statements. START
TRANSACTION begins the transaction. COMMIT makes all changes permanent. ROLLBACK
undoes all changes since the last START TRANSACTION. Together they enforce Atomicity and
Durability.
START TRANSACTION;
-- one or more SQL statements
COMMIT; -- make permanent
ROLLBACK; -- undo all changes
2. SAVEPOINT / ROLLBACK TO SAVEPOINT
A SAVEPOINT creates a named checkpoint inside a transaction. You can roll back to a
specific savepoint without undoing the entire transaction. This provides partial rollback capability and
is useful for complex multi-step operations.
SAVEPOINT savepoint_name;
ROLLBACK TO SAVEPOINT savepoint_name;
RELEASE SAVEPOINT savepoint_name;
3. SET autocommit
By default MySQL auto-commits each statement. Setting autocommit = 0 forces explicit
COMMIT or ROLLBACK for every transaction, giving you full control over when changes become
permanent.
SET autocommit = 0; -- disable auto-commit
SET autocommit = 1; -- restore auto-commit (default)
4. SELECT ... FOR UPDATE
Locks the selected rows for the duration of the current transaction. Other transactions trying
to read or modify those rows must wait. This enforces Isolation by preventing dirty reads and lost
updates in concurrent environments.
SELECT column_list
FROM table_name
WHERE condition
FOR UPDATE;
5. CONSTRAINT CHECK (on table creation)
CHECK constraints validate that column values satisfy a given condition before insertion or
update. They enforce Consistency by rejecting any data that would leave the database in an invalid
state (e.g., stock quantity cannot go below zero).
CONSTRAINT constraint_name CHECK (condition)

Aim:
To use the SQL window ranking functions ROW_NUMBER(), RANK(), DENSE_RANK(),
and PERCENT_RANK() to rank products based on their sales performance (total revenue), and to
compare how each function behaves when two or more products have tied sales figures.
Procedure:
The following algorithm is executed in sequence:
1. Identify the entities required for the scenario: PRODUCT (master data) and SALES
(transaction data).
2. Design the PRODUCT table with product_id, product_name, category, and price.
3. Design the SALES table with sale_id, product_id (foreign key), sale_date, quantity,

4. Create the database and both tables in MySQL using CREATE TABLE with PRIMARY
KEY and FOREIGN KEY constraints.
5. Insert sample PRODUCT and SALES records, including at least one intentional tie in total
revenue between two products, to observe rank behaviour on ties.
6. Write an aggregate query using SUM() and GROUP BY to compute total_units_sold and
total_revenue for every product.
7. Wrap the aggregate query as a derived table (sub-query) and apply ROW_NUMBER() OVER
(ORDER BY total_revenue DESC) to assign a unique sequential number to every row.
8. Apply RANK() OVER (ORDER BY total_revenue DESC) on the same derived table and
observe that tied rows receive an identical rank, and the next rank is skipped.
9. Apply DENSE_RANK() OVER (ORDER BY total_revenue DESC) and observe that tied
rows receive an identical rank, but the next rank is NOT skipped.
10. Apply PERCENT_RANK() OVER (ORDER BY total_revenue DESC) to compute the
relative standing of each product as a percentile between 0 and 1.
11. Combine all four ranking functions in a single SELECT statement to compare their outputs
side by side.
12. Apply PARTITION BY category along with RANK() to rank products within each category
independently.
13. Execute all queries, verify the output against the expected ranking logic, and record the
results.
Relational Schema Diagram:
PRODUCT and SALES are related in a One-to-Many (1:N) relationship — one product can appear in
many sales transactions, connected through the product_id foreign key.

SQL Syntax Reference:
The following window (analytic) functions are used in this experiment. All of them require an
OVER() clause; PARTITION BY inside OVER() is optional and restarts the ranking for every group.
1. ROW_NUMBER()
Assigns a unique, strictly sequential integer to every row in the result set, in the given order. Even if
two rows are tied on the ORDER BY expression, they still get different numbers.
ROW_NUMBER() OVER (
[PARTITION BY partition_expression]
ORDER BY sort_expression [ASC|DESC]
) AS row_num
2. RANK()
Assigns the same rank to tied rows, then skips the following rank(s) by the number of tied rows (gaps
appear after ties).
RANK() OVER (
[PARTITION BY partition_expression]
ORDER BY sort_expression [ASC|DESC]
) AS rank_value
3. DENSE_RANK()
Assigns the same rank to tied rows, but the next rank continues consecutively with no gaps.
DENSE_RANK() OVER (
[PARTITION BY partition_expression]
ORDER BY sort_expression [ASC|DESC]
) AS dense_rank_value
4. PERCENT_RANK()
Returns the relative rank of each row as a value between 0 and 1, calculated as (rank − 1) / (total_rows
− 1). The top row always returns 0, and the last row always returns 1.
PERCENT_RANK() OVER (
[PARTITION BY partition_expression]
ORDER BY sort_expression [ASC|DESC]
) AS percent_rank_value

CREATE PROCEDURE sp_transfer_funds (
IN p_from_acc INT,
IN p_to_acc INT,
IN p_amount DECIMAL(12,2)
)
BEGIN
DECLARE v_from_balance DECIMAL(12,2);
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
ROLLBACK;
SELECT 'Transaction Failed - Rolled Back' AS message;
END;
START TRANSACTION;
SAVEPOINT sp_before_debit;
SELECT balance INTO v_from_balance
FROM Account
WHERE account_no = p_from_acc
FOR UPDATE;
IF v_from_balance IS NULL THEN
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Source account does not exist';
ELSEIF v_from_balance < p_amount THEN
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient balance in source
account';
END IF;
UPDATE Account SET balance = balance - p_amount WHERE account_no = p_from_acc;
INSERT INTO Transaction_Log (account_no, txn_type, amount, description, status)
VALUES (p_from_acc, 'Debit', p_amount, CONCAT('Transfer to account ', p_to_acc),
'Success');
SAVEPOINT sp_after_debit;

UPDATE Account SET balance = balance + p_amount WHERE account_no = p_to_acc;
INSERT INTO Transaction_Log (account_no, txn_type, amount, description, status)
VALUES (p_to_acc, 'Credit', p_amount, CONCAT('Transfer from account ', p_from_acc),
'Success');
COMMIT;
SELECT 'Transaction Successful' AS message;
END$$
DELIMITER;

Normalization:
The relational schema derived from the ER diagram is verified against the first three normal forms:
1NF (Atomicity)
Every column holds a single atomic value. Answer options are stored as four separate
columns (option_a–option_d) instead of one comma-separated list, and a student's answer is one row
per question in STUDENT_ANSWER instead of a repeating group — so no column stores multiple
values.
2NF (No Partial Dependency)
Both many-to-many relationships (Student–Exam and Registration–Question) are resolved
into bridge tables (REGISTRATION, STUDENT_ANSWER) that use a single-column surrogate
primary key (registration_id, answer_id) rather than a composite key, so no non-key attribute depends
on only part of the key.
3NF (No Transitive Dependency)
In every table, non-key attributes depend only on the primary key. The one deliberate
exception is RESULT.grade and RESULT.status, which are functionally dependent on percentage
rather than directly on registration_id. This redundancy is intentional and controlled: both columns are
written only by the sp_evaluate_result procedure, never entered manually, so the table stays consistent
while avoiding a grade look-up join on every report query.

Step 12 — Create Trigger: Auto-Evaluate Answer Correctness
DELIMITER $$
CREATE TRIGGER trg_before_answer_insert
BEFORE INSERT ON Student_Answer
FOR EACH ROW
BEGIN
DECLARE v_correct VARCHAR(1);
SELECT correct_option INTO v_correct
FROM Question WHERE question_id = NEW.question_id;
IF NEW.chosen_option = v_correct THEN
SET NEW.is_correct = 1;
ELSE
SET NEW.is_correct = 0;
END IF;
END$$
DELIMITER;

CREATE TRIGGER trg_after_result_update
AFTER UPDATE ON Result
FOR EACH ROW
BEGIN
IF OLD.total_score <> NEW.total_score OR OLD.grade <> NEW.grade THEN
INSERT INTO Result_Audit
(registration_id, old_score, new_score, old_grade, new_grade, changed_at)
VALUES
(OLD.registration_id, OLD.total_score, NEW.total_score,

OLD.grade, NEW.grade, NOW());
END IF;
END$$
DELIMITER;
Step 14 — Create Procedure: Register Student for Exam
DELIMITER $$
CREATE PROCEDURE sp_register_student (
IN p_student_id INT,
IN p_exam_id INT
)
BEGIN
DECLARE v_count INT;
SELECT COUNT(*) INTO v_count
FROM Registration
WHERE student_id = p_student_id AND exam_id = p_exam_id;
IF v_count > 0 THEN
SIGNAL SQLSTATE '45000'
SET MESSAGE_TEXT = 'Student already registered for this exam';
ELSE
INSERT INTO Registration (student_id, exam_id, registered_at)
VALUES (p_student_id, p_exam_id, NOW());
END IF;
END$$
DELIMITER;
Step 15 — Create Procedure: Evaluate Result
DELIMITER $$
CREATE PROCEDURE sp_evaluate_result (
IN p_registration_id INT
)
BEGIN
DECLARE v_score INT;
DECLARE v_total_marks INT;
DECLARE v_exam_id INT;
DECLARE v_pct DECIMAL(5,2);
DECLARE v_grade VARCHAR(2);
DECLARE v_status VARCHAR(10);
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
ROLLBACK;
RESIGNAL;
END;

START TRANSACTION;
SELECT exam_id INTO v_exam_id
FROM Registration WHERE registration_id = p_registration_id;
SELECT total_marks INTO v_total_marks
FROM Exam WHERE exam_id = v_exam_id;
SELECT COALESCE(SUM(q.marks), 0) INTO v_score
FROM Student_Answer sa
INNER JOIN Question q ON sa.question_id = q.question_id
WHERE sa.registration_id = p_registration_id AND sa.is_correct = 1;
SET v_pct = ROUND((v_score / v_total_marks) * 100, 2);
SET v_grade = CASE
WHEN v_pct >= 90 THEN 'A+'
WHEN v_pct >= 75 THEN 'A'
WHEN v_pct >= 60 THEN 'B'
WHEN v_pct >= 40 THEN 'C'
ELSE 'F'
END;
SET v_status = CASE WHEN v_pct >= 40 THEN 'Pass' ELSE 'Fail' END;
INSERT INTO Result
(registration_id, total_score, percentage, grade, status, evaluated_at)
VALUES
(p_registration_id, v_score, v_pct, v_grade, v_status, NOW())
ON DUPLICATE KEY UPDATE
total_score = v_score,
percentage = v_pct,
grade = v_grade,
status = v_status,
evaluated_at = NOW();
COMMIT;
END$$
DELIMITER;
